## 질문 키워드로 규정 파일 선택

`app/gemini_client.py`의 `REGULATION_KEYWORDS`는 파일명과 질문 키워드를 연결한다.
`select_regulation_files()`가 질문에서 일치하는 파일을 고르고,
`load_regulations()`가 `data/regulations/`에서 그 파일들만 `open()`으로 읽는다.
`build_system_prompt()`는 선택한 본문을 `[참고 규정]`에 넣는다.

| 질문 | 선택하는 파일 |
| --- | --- |
| 월급은 언제 들어오나요? | 급여규정.md |
| 자기 계발비 얼마까지 지원되나요? | 복리후생규정.md |
| VPN 설치 방법은? | 정보보안_IT이용규정.md |
| 배우자 출산휴가와 경조사비는? | 휴가_근태규정.md, 복리후생규정.md |
| 쉽게 설명해줘 | 최근 사용자 질문의 규정(명확한 후속 질문일 때) |
| 자기계발비 질문 후 '영수증은 언제까지?' | 복리후생규정.md (출장 규정으로 바꾸지 않음) |
| 새 대화에서 '영수증은 언제까지?' | 선택 없음, 비용 종류 확인 |

- 구체적인 새 주제의 키워드가 있으면 현재 질문을 우선한다. 과거의 모든 규정을 합치지 않는다.
- `COMMON_KEYWORDS`의 영수증·증빙은 여러 제도의 공통 단어다. 이전 주제를 확인하고,
  주제가 없으면 `AMBIGUOUS_KEYWORDS`를 기준으로 필요한 비용 종류를 묻는다.
- 키워드가 없으면 파일을 읽지 않는다. 업무 규정 질문이면 분야를 확인하도록 지시한다.
  키워드 미일치는 규정 부재가 확정된 것이 아니다.
- 선택한 문서에 제도가 없으면 `규정에는 없는 내용입니다.`라고 안내한다.
  일부 조건만 있는 경우에는 있는 기준과 미기재 사항, 문서의 문의처를 구분한다.
- 키워드는 공백·구분자·영문 대소문자를 정리해 비교한다. 동의어·새 파일은
  `REGULATION_KEYWORDS`에 직접 추가해야 한다. 모든 표현을 자동으로 이해하는 검색은 아니다.
- 선택한 MD는 매 질문마다 읽으므로 UTF-8로 저장한 변경이 다음 질문에 반영된다.
- 전송할 때 검색 키워드 목록과 항목 식별 코드만 제거한다. 규정 본문과 원본 파일은 유지한다.
- 선택한 파일 누락·빈 파일·읽기 오류는 메시지 저장과 Gemini 호출 전에 HTTP 503으로 처리한다.
- 전체 MD를 보내던 경우보다 규정 본문 입력량이 줄어든다. 지침·질문·최근 대화는 계속 전달되므로
  실제 총 토큰 절감량은 선택 파일과 대화 길이에 따라 달라진다.

기존 `POST /conversations/{conversation_id}/chat`, Gemini `system_instruction`,
Supabase 저장, Redis 대화 이력, 프런트엔드 SSE 표시 구조를 사용한다.

## 답변 품질 점검

`BASE_PROMPT`는 문서의 조건·예외, 부분적으로만 확인되는 내용, 후속 질문과 새 주제를
구분하도록 작성했다. `build_system_prompt()`는 실제 `##` 항목명으로 인용 표기를 만든다.
모델·API·패키지는 추가하지 않았으며, 일반 채팅에서 Gemini 호출은 기존처럼 한 번이다.

수정 후에는 다음 질문을 별도 대화와 연속 대화에서 확인한다.

- 월급날이 휴일인 경우 → 직전 영업일
- 자기계발비 문의 후 영수증 기한 → 결제 후 30일
- 종류 없이 영수증 기한 문의 → 비용 종류 확인
- 책값·비번 등 구어체 → 해당 규정 안내
- 명시되지 않은 자가용 km당 단가 → 금액을 만들지 않고 미기재·재무팀 확인 안내
- 개인별 잔여 연차 → 조회한 척하지 않고 실제 확인 메뉴 안내

키워드 기반이므로 등록되지 않은 표현은 추가 확인이 필요할 수 있다. 프롬프트는 모델의
오류를 완전히 막는 장치가 아니므로 중요한 숫자·조건은 원문과 함께 검토한다.

## 분석 대시보드 API

모든 분석 API는 로그인 토큰 `Authorization: Bearer <access_token>`이 필요하며 전체 사용자의 로그를 조회한다.
로그인한 모든 사용자가 접근할 수 있으며 별도의 관리자 등록은 필요하지 않다.
기존 일반 사용자 대화 API의 소유자 제한은 변경하지 않는다.
Swagger `/docs`에서 Authorize 후 테스트할 수 있다.

| 메서드 | 주소 | 용도 |
| --- | --- | --- |
| GET | `/analytics/summary` | 요청 수, 토큰 합계, 평균·p95 응답 시간, 대화 수 |
| GET | `/analytics/conversations` | 대화별 통계, 요청 수 내림차순 |
| GET | `/analytics/logs` | 로그 상세 목록, 기록 시각 내림차순 |

공통 쿼리:

- `start`, `end`: 시간대가 포함된 ISO 8601 시각. `start` 포함, `end` 제외.
  생략하면 `end`는 현재, `start`는 `end`의 30일 전이다. 최대 조회 기간은 366일이다.
- `conversation_id`: 선택적 대화 UUID. 소유자 제한 없이 조회하며 DB와 Redis 모두에 없는 대화는 404.
- `/logs`, `/conversations`의 `limit`: 기본 50, 1~200. `offset`: 기본 0, 0 이상.
  응답 `total`은 페이지를 나누기 전 결과 개수다.

예: `/analytics/summary?start=2026-09-01T00:00:00Z&end=2026-09-08T00:00:00Z`

통계의 `request_count`는 해당 기간에 남아 있는 성공 응답 로그 수다.
`conversation_count`는 전체 DB 대화와 Redis에만 남은 대화를 합친 수(기간 내 생성 건수가 아님),
`active_conversation_count`는 기간 내 로그가 있는 대화 수다.
대화별 목록에는 기간 내 로그가 없는 대화도 0건으로 포함된다.
토큰 합계는 알려진 값만 더하며 일부 토큰 정보가 없는 로그 수를
`missing_usage_count`로 제공한다. 빈 결과의 지연 시간은 `null`이다.
p95는 정렬한 지연 시간에서 nearest-rank 방식으로 계산한다.

### 데이터 범위와 보관

현재 Redis의 모든 `usage_log:*` 목록을 분석한다. 저장 측에서 **대화별 최근 50건**만 유지하므로 이미 삭제된 과거 로그는 복구할 수 없다. `coverage.scope`는 `all_users`다.
오래된 기록은 이미 잘려 있을 수 있으므로 전체 기간의 누적 통계로 해석하면 안 된다.
응답 `coverage.complete_history=false`와 `max_logs_per_conversation=50`으로 이 범위를 표시한다.
`requested_at`은 기존 저장 코드 기준 로그 저장 시각이며 요청 시작 시각이 아니다.
실패 요청은 수집되지 않으므로 오류율을 계산할 수 없다.
삭제된 대화도 Redis에 로그가 남아 있으면 포함하고 제목은 `삭제되었거나 정보가 없는 대화`로 표시한다. 잘못된 JSON/필드의 로그는 제외하고
`coverage.skipped_invalid_logs`에 읽은 로그 중 제외한 개수를 표시한다(기간 필터 적용 전).
Redis 장애는 503, 잘못된 쿼리는 422를 반환한다.

이번 API는 저장 방식과 TTL을 변경하지 않는다. 장기 분석에는 별도의 영구 로그 저장소가 필요하다.
조회마다 전체 대화와 Redis 사용량 로그를 읽으므로 대화가 아주 많은 경우 사전 집계가 필요하다.
요청 간 새 로그가 추가되면 페이지 결과나 각 API의 통계가 달라질 수 있다.
